# 个人套餐与积分计费方案

> 状态：费率影子记录已实现；套餐额度等待长全文真实双模型基准确认
> 版本：v1.0（2026-10-08）  
> 适用范围：个人用户、兑换码开通、AI 初筛与 AI 质量评价等模型调用场景  
> 不在本期范围：团队空间、共享额度、自助微信/支付宝支付、自动续费

## 1. 结论

首发保留现有免费体验能力，新增三个个人付费套餐：

| 套餐 | 月付价格 | 套餐积分/月 | AI 并发 | 项目上限 | 适合人群 |
|---|---:|---:|---:|---:|---|
| Lite | ¥399/月 | 15,000 | 4 | 5 | 每月完成约 1 个标准工作量项目的个人用户 |
| Plus | ¥599/月 | 40,000 | 8 | 10 | 持续开展多个综述项目的个人用户 |
| Pro | ¥899/月 | 100,000 | 16 | 20 | 高频批量使用、多项目并行的重度个人用户 |

价格、自然月有效期、积分和权益必须以后台商品版本配置，不能写死。这里的“月付”按开通时间增加一个自然月计算，例如 1 月 15 日开通，到期时间为 2 月 15 日同一时刻；不要简单写成固定 30 天。

核心原则如下：

1. 免费体验不是第四个正式套餐。未购买套餐的用户继续沿用当前注册赠送积分和现有免费体验流程。
2. 三个套餐均为个人套餐，不提供成员、席位、共享积分池或团队管理员功能。
3. 所有套餐均可使用平台当前开放的模型，不用“高价套餐才能选好模型”人为设限；昂贵模型通过更高积分消耗体现成本。
4. 积分不再直接等于总 Token 数。按模型、输入、输出、缓存及上下文价格档位分别折算。
5. 前端显示简洁的“约 N 倍积分消耗”，后台使用精确费率结算；展示倍率只用于比较和预估，不作为最终账单公式。
6. 套餐积分按月发放和到期，不将未使用月度积分无限滚存。
7. 先使用兑换码开通和续费，但数据结构按未来接入微信、支付宝和订单支付的要求设计，避免二次重构。

## 2. 为什么不再使用“总 Token / 1000”

当前实现将所有模型的 `prompt_tokens + completion_tokens` 相加后，按固定 Token 比例折算积分。这会产生四个问题：

- 不同模型每百万 Token 的供应商价格相差数倍甚至数十倍。
- 同一模型的输出 Token 通常明显贵于输入 Token，不能混成一个总数。
- 缓存命中输入往往比普通输入便宜，直接按普通 Token 收费不准确。
- 多模型任务目前只保存模型列表和合计 Token，无法追溯每个模型分别用了多少、按哪个费率结算。

Codex 和 Claude 的商业产品也没有把“一个原始 Token”直接承诺为固定使用权益。Codex 的可用量会随模型、任务复杂度、上下文、推理强度和工具使用变化，并允许在套餐额度外购买 credits；Claude 的 API 定价则明确区分输入、输出、缓存写入和缓存读取。这个项目应采用相同思路：套餐提供可理解的积分额度，后台把真实资源消耗换算成积分，而不是把积分伪装成 Token。

## 3. 积分定义

### 3.1 基准单位

定义：

> **1 积分 = 1,000 个 DeepSeek V4 Flash 普通输入 Token 的成本等价值。**

DeepSeek V4 Flash 是当前平台默认模型，因此将它作为 `1.0×` 基准，迁移后用户最常用模型的消费体感不会发生数量级变化。

积分是平台内部使用权益，不等于人民币、不可提现、不可转账，也不承诺与供应商 Token 一一对应。供应商调价时通过新增费率版本调整，不追溯修改已完成任务。

### 3.2 精确结算公式

每次任务按“模型调用明细”累计，任务结束后再统一向上取整：

```text
模型积分原值 =
    普通输入 Token × 输入权重
  + 缓存命中 Token × 缓存读取权重
  + 缓存写入 Token × 缓存写入权重
  + 输出 Token × 输出权重
  + 供应商明确单列的其他计费项

任务实际积分 = max(1, ceil(所有模型积分原值之和 / 1000))
```

权重计算：

```text
某计费项权重 = 该模型该计费项的人民币单价 / DeepSeek V4 Flash 普通输入人民币单价
```

补充规则：

- 美元价格使用后台配置的汇率版本换算，首版测算汇率取 `1 USD = 7.20 CNY`，不是实时浮动汇率。
- 上下文阶梯价格按单次请求的实际输入长度选择对应档位。
- 如果供应商把推理 Token 包含在输出 Token 中，只计一次；只有供应商单独计价且未包含在输出用量中时才新增计费项。
- 如果接口没有返回缓存明细，按普通输入计费，不能猜测缓存命中量。
- 按任务、按模型汇总后取整，不对每篇文献或每次小请求分别向上取整，避免大量碎片请求造成不合理放大。
- 无任何已计费用量的失败请求不扣积分；供应商已返回用量的失败或重试请求按实际用量记录。
- 管理员继续免扣积分，但必须完整记录等价积分和模型成本，便于经营核算。

## 4. 首版模型倍率

### 4.1 计算口径

下表使用 2026-10-08 查阅到的公开标准价格作为设计快照；人民币模型使用中国大陆标准实时推理价，美元模型按 `7.20` 汇率换算。供应商活动折扣、免费额度、夜间优惠和 Batch 折扣不直接返还给用户，避免同一任务因调用时间不同而产生不可解释的积分差异。

“前台综合倍率”按典型文献任务 `85% 输入 + 15% 输出` 计算，并以 DeepSeek V4 Flash 为 `1.0×`。最终扣费仍按输入和输出权重分别计算。

| 平台模型 | 价格快照（每百万 Token） | 输入权重 | 输出权重 | 前台综合倍率 | 建议前台文案 |
|---|---:|---:|---:|---:|---|
| Qwen3.7-Flash | 输入 ¥0.20 / 输出 ¥0.80（≤32K） | 0.093 | 0.370 | 约 0.1× | 极省积分 |
| Qwen3.7-Plus | 输入 ¥2.00 / 输出 ¥8.00（≤256K） | 0.926 | 3.704 | 约 0.9× | 均衡消耗 |
| DeepSeek V4 Flash | 输入 $0.30 / 输出 $1.20 | 1.000 | 4.000 | 1.0× | 标准消耗 |
| Doubao-Seed-2.1-Turbo | 输入约 ¥3.00 / 输出约 ¥15.00 | 1.389 | 6.944 | 约 1.5× | 中等消耗 |
| DeepSeek V4 Pro | 输入 $1.32 / 输出 $3.96 | 4.400 | 13.200 | 约 3.9× | 较高消耗 |
| Qwen3.7-Max | 输入 ¥12.00 / 输出 ¥36.00 | 5.556 | 16.667 | 约 5.0× | 高消耗 |

注意：

- Qwen3.7-Flash 在输入超过 32K 后有更高价格档位，后台必须按供应商阶梯配置动态选权重，不能永远使用 `0.1×`。
- 缓存读取和缓存写入权重必须独立配置。某模型尚未确认或 API 未返回缓存用量时，首版保守地按普通输入权重结算。
- 上述倍率属于“费率版本 v1”，上线前需再次核对实际开通地域、实际 API Model ID 和供应商账单单价。
- 前端模型卡片显示“预计约 1.5× 积分”，任务确认页展示预计积分区间；账单明细显示最终实际积分及输入、输出用量。

### 4.2 示例

假设某次任务使用 `1,500` 输入 Token 和 `300` 输出 Token：

```text
DeepSeek V4 Flash：
(1500 × 1.0 + 300 × 4.0) / 1000 = 2.7 → 任务汇总后参与取整

Doubao-Seed-2.1-Turbo：
(1500 × 1.389 + 300 × 6.944) / 1000 ≈ 4.17

Qwen3.7-Max：
(1500 × 5.556 + 300 × 16.667) / 1000 ≈ 13.33
```

如果一个任务包含 100 篇文献，应先汇总 100 篇以及所有重试的实际用量，最后只进行一次向上取整。

## 5. 标准工作量积分测算

### 5.1 测算目标

用以下工作量作为一个“标准月度项目预算单元”：

- 2,000 篇文献；
- 使用 DeepSeek V4 Flash + Qwen3.7-Flash 双模型完成 AI 初筛；
- 其中 100 篇文献继续使用相同双模型完成 AI 质量评价。

### 5.2 样本依据

本次没有仅根据 Prompt 字符数估算，而是使用当前本地数据库中、最新代码产生的真实 Token 日志：

| 环节 | 样本 | 每篇每模型平均输入 | 每篇每模型平均输出 | 说明 |
|---|---:|---:|---:|---|
| AI 初筛 | 974 篇双模型任务 | 约 3,700 | 约 60 | 采用 2026-10-08 最新任务，已经包含当前较长的初筛 Prompt |
| AI 质量评价（旧链路） | 6 篇单模型任务 | 约 4,866 | 约 1,590 | 仅代表旧的前 8,000 字符链路，不再用于新版额度定案 |
| AI 质量评价（新链路本地基准） | 30 篇 QUADAS-2 全文 | P50 约 25,852；P75 约 28,446；P90 约 35,120 | 尚待真实双模型基准 | 完整提取、按领域检索；30/30 成功且未截断 |

新版质量评价不再固定截取全文前 8,000 字符，而是按领域发送有页码的证据包。30 篇本地基准的输入规模已经明显高于旧样本；由于尚未获得将测试全文证据发送给外部模型的明确授权，目前没有真实输出 Token、重试率和供应商账单数据。因此旧质量评价数字只能作为历史对照，不能继续作为套餐定价依据。

### 5.3 计算过程

DeepSeek V4 Flash 的输入、输出权重分别为 `1.0` 和 `4.0`；Qwen3.7-Flash 的输入、输出权重分别为 `0.0926` 和 `0.3704`。

AI 初筛：

```text
DeepSeek 每篇 = (3,700 × 1.0 + 60 × 4.0) / 1000
               ≈ 3.940 积分

Qwen 每篇     = (3,700 × 0.0926 + 60 × 0.3704) / 1000
               ≈ 0.365 积分

2,000 篇双模型初筛 ≈ (3.940 + 0.365) × 2,000
                   ≈ 8,607 积分
```

AI 质量评价（旧链路历史值，仅作对照）：

```text
DeepSeek 每篇 = (4,866 × 1.0 + 1,590 × 4.0) / 1000
               ≈ 11.226 积分

Qwen 每篇     = (4,866 × 0.0926 + 1,590 × 0.3704) / 1000
               ≈ 1.039 积分

100 篇双模型质量评价 ≈ (11.226 + 1.039) × 100
                     ≈ 1,226 积分
```

合计：

```text
旧链路样本中心值 = 8,607 + 1,226 = 9,833 积分
旧估算增加 25% 波动余量 ≈ 12,292 积分
旧套餐预算取整 = 12,500 积分（新版长全文链路不再沿用为定案值）
```

当前暂不把 **12,500 积分** 定义为新版标准月度项目预算单元。仅按本地基准的输入 Token 计算，100 篇 DeepSeek Flash + Qwen Flash 双模型质量评价的输入部分约为：P50 2,825、P75 3,109、P90 3,838 积分，尚未包含输出和重试。待真实基准补齐后，应以真实 P75 加安全余量重新计算完整标准工作量，再确认 Lite/Plus/Pro 的月度积分是否维持 15,000/40,000/100,000。

### 5.4 额度建议

以下月度积分作为当前产品候选值保留，但不在真实长全文基准完成前对外承诺固定工作量：

| 套餐 | 月度积分候选值 | 当前状态 | 设计含义 |
|---|---:|---|---|
| Lite | 15,000 | 待真实基准确认 | 目标是覆盖一个标准月度项目并留少量复跑空间 |
| Plus | 40,000 | 待真实基准确认 | 相比 Lite 显著提高多项目处理能力 |
| Pro | 100,000 | 待真实基准确认 | 支持高频处理和较多复跑，同时保持成本边界 |

上线前先用 30 篇以上真实双模型样本完成第一次校准；首发后继续记录至少 30 天。如果实际 P75 超过当期标准工作量预算，再通过下一商品版本调整月度额度，不追溯减少已经发放的积分。

## 6. 套餐设计

### 6.1 免费体验

- 保留当前注册、激活和欢迎积分能力，不新增“Free”付费商品。
- 欢迎积分数继续由现有后台配置控制（当前默认 200），不在套餐代码中写死。
- 免费用户继续使用现有基础功能；模型不同会按新倍率产生不同消耗。
- 上线新公式前，需要用真实任务回放验证当前欢迎积分是否仍能完成一次有意义的完整体验，但不能直接清零或作废存量积分。

按“每篇约 1,500 输入 + 300 输出 Token”的示例估算，200 积分大约可完成 74 篇 DeepSeek V4 Flash 文献处理，和现有免费体验定位基本一致；这只是测算值，前端不能承诺固定篇数。

### 6.2 Lite — ¥399 / 月

- 每月 15,000 套餐积分。
- 同时运行 4 个 AI 任务。
- 最多保留 5 个项目。
- 标准任务队列。
- 完整个人工作流：文献解析、去重、人工审阅、AI 初筛、质量评价和导出。
- 建议存储配额 5 GB。
- 适合低频个人用户，不提供团队功能。

### 6.3 Plus — ¥599 / 月

- 每月 40,000 套餐积分。
- 同时运行 8 个 AI 任务。
- 最多保留 10 个项目。
- 高于 Lite 的队列权重，但必须设置防饥饿规则。
- 建议存储配额 20 GB。
- 其他核心研究功能与 Lite 相同，主要差异是额度、吞吐量和存储空间。

### 6.4 Pro — ¥899 / 月

- 每月 100,000 套餐积分。
- 同时运行 16 个 AI 任务。
- 最多保留 20 个项目。
- 个人版最高队列权重，但仍受系统全局并发和安全上限约束。
- 建议存储配额 50 GB。
- 不包含组织、团队成员、共享项目或共享积分池；这些能力以后单独设计团队版。

### 6.5 项目数量口径

- 项目上限指当前账户下尚未删除、仍可访问的项目总数，不按筛选项目和质量评价项目分别计算。
- 达到上限后禁止新建项目，但不影响查看、执行和导出现有项目。
- 用户降档或套餐过期后，如果已有项目数超过新上限，不自动删除或锁定历史项目，只禁止继续新建，直到数量低于上限。
- 删除项目属于不可逆数据操作，不能为了腾出名额自动执行；必须继续由用户明确确认。

### 6.6 套餐价值校验

按 DeepSeek V4 Flash 基准成本估算，15,000 / 40,000 / 100,000 积分对应的供应商基准成本上限约为 ¥32 / ¥86 / ¥216。尚未计入服务器、文件存储、邮件、运维、失败重试、税费、客服和支付通道成本，因此三个档位仍保留了安全空间，并且高档位的单位积分价格逐级下降。

正式上线前应使用至少 30 天真实调用数据重新计算：

- 各模型调用占比；
- 每篇文献平均输入和输出 Token；
- 失败及自动重试率；
- 质量评价全文带来的长上下文成本；
- 单用户峰值并发和存储成本；
- 实际供应商账单与平台计算成本的误差。

如果 Pro 的供应商成本长期超过套餐实收金额的 35%，应优先调整下一价格版本的包含积分或模型费率，不能追溯扣除用户已获得的积分。

## 7. 兑换码开通与续费

### 7.1 兑换码商品化

现有兑换码不能再只有一个 `credits` 数字。计划新增：

```text
code_type       = PLAN | CREDIT
plan_code       = LITE | PLUS | PRO | null
price_version   = 价格版本
valid_months    = 1
credit_amount   = 套餐积分
batch_no        = 发放批次
expires_at      = 兑换码本身失效时间
redeemed_by     = 使用用户
redeemed_at     = 使用时间
```

- `PLAN` 码开通或续费套餐并发放一个积分批次。
- `CREDIT` 码只补充积分，用于售后补偿、活动或未来单独积分包，不改变套餐等级。
- 每个兑换码只能成功使用一次，数据库唯一约束和事务锁共同保证并发兑换不会重复发放。

### 7.2 续费和换档规则

- 当前没有生效套餐：兑换后立即开通一个自然月，并发放本周期月度积分。
- 同档续费：在当前到期日后顺延一个自然月，下一周期积分到下一周期开始时才生效，不能提前透支。
- 升档或降档：兑换后安排在当前周期结束时生效；首版不做按日补差、立即换档或剩余天数折算。
- 同一账户只能有一个待生效套餐，已经排期后再次兑换时必须明确提示并拒绝，避免用户误操作。
- 套餐过期：用户回到免费体验状态，历史项目和数据仍可查看、导出；新任务按免费状态权限执行。
- 兑换码输错、过期或不适用时不得产生任何账户变更。

首版采用上述简单规则，避免手工兑换场景引入复杂的补差价、退款和按日折算。接入自助支付后再增加订单级升级和退款规则。

## 8. 积分批次和消费顺序

当前单一 `balance` 无法表达套餐积分、赠送积分和不同有效期。需要增加积分批次账本：

| 批次类型 | 建议有效期 | 是否可退款 | 说明 |
|---|---:|---:|---|
| WELCOME | 沿用当前规则 | 否 | 注册体验赠送 |
| PLAN | 对应套餐月度周期结束 | 随套餐退款规则 | Lite / Plus / Pro 附带积分 |
| PURCHASED | 商品配置 | 视订单规则 | 为未来积分包预留 |
| PROMOTION | 活动配置 | 否 | 运营活动赠送 |
| COMPENSATION | 后台配置 | 否 | 故障或售后补偿 |
| LEGACY | 不早于迁移前规则 | 否 | 迁移已有余额，保证不丢失 |

消费顺序采用：

1. 最早过期的可用批次优先；
2. 到期日相同，先消耗不可退款积分；
3. 永久积分最后消耗；
4. 每次扣费记录具体消耗了哪些批次，退款时只反向恢复原批次，不凭空生成新积分。

积分过期必须生成账本流水，不直接静默修改余额。用户余额等于所有有效批次剩余量之和，缓存余额只作为加速字段，可以由账本重建。

## 9. 预估、预占和最终结算

为了避免用户同时启动多个任务导致余额穿透，采用三段式流程：

```text
预估 → 原子预占 → 实际结算
```

1. **预估**：按文献抽样、Prompt 模板、模型费率和历史 P95 输出长度给出预计区间。
2. **预占**：任务创建时在事务内锁定账户和批次，将预计上限从“可用余额”移入“冻结余额”。
3. **执行**：逐次记录每个模型调用的输入、缓存、输出、重试和供应商请求 ID。
4. **结算**：任务结束后按创建时冻结的费率版本计算实际积分，多余冻结额度释放，实际不足部分在允许上限内补扣。
5. **异常恢复**：任务失败或取消时仍结算供应商已经产生的真实用量，其余冻结额度释放；结算操作必须幂等。

当余额不足以完成预占时，不启动任务，并向用户展示“预计需要、当前可用、不同模型预计消耗”而不是笼统提示余额不足。

费率在任务创建时冻结。即使管理员在任务运行期间发布新费率，这个任务也继续使用旧版本，保证可解释性。

## 10. 数据模型建议

建议在现有账户和流水基础上增量扩展，不替换 Django User：

| 模型 | 作用 |
|---|---|
| `PlanCatalog` | Lite / Plus / Pro 的稳定产品标识 |
| `PlanPriceVersion` | 价格、有效月数、包含积分、并发、项目上限及生效时间 |
| `UserPlanEntitlement` | 用户当前套餐、开始/到期时间、来源兑换码或订单 |
| `CreditGrantBatch` | 每笔积分来源、总量、剩余量和到期时间 |
| `CreditTransaction` | 保留总账流水，并关联批次明细、任务和幂等键 |
| `CreditAllocation` | 一次消费跨多个积分批次时的分摊明细 |
| `ModelBillingRate` | 模型、地区、币种、汇率、输入/输出/缓存权重、上下文阶梯和版本 |
| `ModelUsageDetail` | 每次或每模型调用的 Token 分类、请求 ID、费率版本和积分结果 |
| `CreditReservation` | 任务预占、释放、结算和状态机 |
| `RechargeCode` | 扩展套餐、价格版本、积分、有效月数和批次字段 |

关键约束：

- 费率、价格和权益都只新增版本，不原地修改历史快照。
- `ModelUsageDetail` 必须使用平台规范化模型 ID；旧模型别名在请求路由后再落规范化 ID。
- 兑换、预占、结算、退款都使用唯一幂等键。
- 余额、冻结余额、批次剩余额度的更新均使用数据库事务和行锁。
- 用户、任务、项目、兑换码和交易的关联必须保持租户隔离，普通用户只能查看自己的账单明细。

## 11. 前端交互

### 11.1 套餐页

- 三张卡片固定为 Lite、Plus、Pro。
- 明确显示 `¥399/月`、`¥599/月`、`¥899/月`，不要只显示裸价格。
- 展示月度积分、AI 并发、项目上限、存储额度和“仅限个人使用”。
- 当前仍为兑换码模式时，主按钮使用“输入兑换码开通”，不要出现虚假的“立即支付”。
- 用户已有套餐时展示当前等级、到期日、可用积分和续费入口。

### 11.2 模型选择

每个模型显示：

```text
DeepSeek V4 Flash    标准消耗 · 约 1.0×
Qwen3.7-Flash        极省积分 · 约 0.1×
Doubao Seed 2.1      中等消耗 · 约 1.5×
Qwen3.7-Max          高消耗 · 约 5.0×
```

在用户确认运行前显示预计积分区间。长上下文触发更高价格档位时给出提示，例如：“本次单篇上下文可能超过 32K，Qwen3.7-Flash 将按更高档位计费。”

### 11.3 账单页

普通用户至少可以看到：

- 时间、功能、项目、任务；
- 使用模型；
- 输入、输出、缓存 Token；
- 展示倍率和实际积分；
- 预占、释放、消费、退款、过期等流水；
- 当前套餐、积分批次及到期时间。

供应商人民币成本、毛利和内部汇率只在管理员界面显示。

## 12. 配置与管理边界

以下内容应存数据库并通过管理员后台发布版本，而不是放在 `.env`：

- 套餐名称、价格、有效月数、包含积分；
- 套餐并发、存储等权益；
- 各模型输入、输出、缓存和上下文阶梯费率；
- 汇率和费率生效时间；
- 兑换码关联的商品版本。

`.env` 只保留环境级开关和安全兜底，例如：

```text
PLAN_BILLING_ENABLED=false
MODEL_WEIGHTED_BILLING_ENABLED=false
BILLING_RESERVATION_ENABLED=false
BILLING_FX_FALLBACK_CNY_PER_USD=7.20
```

功能开关用于灰度和紧急回退，不能替代数据库价格版本。生产环境切换新计费前必须记录旧公式、迁移批次和切换时间。

## 13. 实施顺序

### 阶段 A：数据与费率基础

- 新增套餐、价格版本、用户权益、积分批次、费率版本和模型用量明细。
- 为当前六个模型建立首版费率快照及上下文阶梯。
- 改造 AI Provider 返回结构，统一提供模型级输入、输出、缓存和供应商请求 ID。
- 多模型任务不再只保存合计 Token 和模型名称列表。

### 阶段 B：新积分引擎

- 实现精确积分计算器、任务预估、原子预占、结算和释放。
- 替换当前 `tokens_to_credits(total_tokens)` 及筛选结果行内的旧折算逻辑。
- 管理员免扣费但记录等价积分。
- 增加重复回调、重复任务结算和并发余额穿透测试。

### 阶段 C：套餐与兑换码

- 扩展兑换码，支持 Lite / Plus / Pro 开通、续费和升级。
- 实现用户套餐状态、到期处理和权益判断。
- 增加套餐后台、批量生成兑换码和导出核销记录。

### 阶段 D：前端

- 新增个人套餐页、当前套餐卡片和兑换入口。
- 模型选择展示综合倍率和预计积分。
- 账户页展示批次余额、到期时间和可解释账单。

### 阶段 E：迁移与灰度

- 将已有余额迁入 `LEGACY` 批次，余额数值不减少。
- 使用历史 Token 日志离线对比旧公式和新公式，不对历史任务补扣。
- 先对管理员执行影子计费，只记录不扣款；确认供应商账单误差后再灰度普通用户。
- 灰度期间保留旧公式回退开关，但同一个任务只能使用一个计费版本。
- 连续观察至少 30 天后再决定是否调整下一版套餐积分和费率。

## 14. 验收标准

1. 同样 Token 用量选择不同模型，会按费率版本产生不同且可复算的积分。
2. 输入、输出、缓存和长上下文阶梯均能独立计价。
3. 多模型任务可以逐模型追踪用量，分项之和等于最终账单。
4. 同一兑换码并发提交只能有一次成功，积分和套餐均只发放一次。
5. 同一任务重复结算不会重复扣费。
6. 多个并发任务不能共同花掉同一份可用积分。
7. 失败、取消、重试和超时均能正确结算真实用量并释放剩余冻结额度。
8. 费率发布后不改变历史任务、历史流水和运行中任务的计算结果。
9. 已有用户余额迁移前后数值一致，历史项目不受套餐状态影响。
10. 普通用户只能查看自己的套餐与账单，管理员能查看全局成本和核销审计。

## 15. 暂不实施的内容

- 微信、支付宝自助支付及自动续费；
- 年付折扣套餐和按日补差价升级；
- 团队空间、席位、共享积分池；
- 积分转赠、提现或用户之间交易；
- 动态夜间折扣、供应商促销价实时传导；
- 基于单个用户议价的个性化费率。

这些能力可以在当前数据模型上继续扩展，但不应进入首版，以免兑换码试运营阶段就承担完整支付和订阅系统的复杂度。
