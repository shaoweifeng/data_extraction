## 1. 结论

首发保留现有免费体验能力，新增三个个人付费套餐：

| 套餐 | 月付价格 | 套餐积分/月 | AI 调用槽位 | 项目上限 | 存储上限 | 适合人群 |
|---|---:|---:|---:|---:|---:|---|
| Lite | ¥399/月 | 20,000 | 4 | 5 | 20 GB | 每月完成约 1 个标准工作量项目的个人用户 |
| Plus | ¥599/月 | 50,000 | 8 | 10 | 50 GB | 持续开展多个综述项目的个人用户 |
| Pro | ¥899/月 | 120,000 | 16 | 20 | 100 GB | 高频批量使用、多项目并行的重度个人用户 |

免费体验账户默认获得一次性 200 欢迎积分、1 个项目名额、2 个用户聚合 AI 调用槽位和 5 GB 存储空间。免费体验不是可购买的第四档套餐。

价格、自然月有效期、积分和权益必须以后台商品版本配置，不能写死。这里的“月付”按开通时间增加一个自然月计算，例如 1 月 15 日开通，到期时间为 2 月 15 日同一时刻；不要简单写成固定 30 天。若起始日为月末，后续周期均保持“月末锚点”；周期采用左闭右开区间 `[开始时间, 到期时间)`，统一按账户时区计算、按 UTC 存储。

核心原则如下：

1. 免费体验不是第四个正式套餐。未购买套餐的用户继续沿用当前注册赠送积分和现有免费体验流程。
2. 三个套餐均为个人套餐，不提供成员、席位、共享积分池或团队管理员功能。
3. 所有套餐均可使用平台当前开放的模型，不用“高价套餐才能选好模型”人为设限；昂贵模型通过更高积分消耗体现成本。
4. 积分不再直接等于总 Token 数。按模型、输入、输出、缓存及上下文价格档位分别折算。
5. 前端显示简洁的“约 N 倍积分消耗”，后台使用精确费率结算；展示倍率只用于比较和预估，不作为最终账单公式。
6. 套餐积分按月发放和到期，不将未使用月度积分无限滚存。
7. 内测期只通过人工沟通后发放兑换码开通或续费，不在咨询功能中保存申请、金额、支付流水或退款信息。未来绑定公司并正式商业化时，再独立设计订单与支付域。
8. 4 / 8 / 16 表示同一用户所有活动任务合计可占用的供应商调用槽位，不是“可同时创建多少个 Celery 任务”。
9. 存储额度与项目数、AI 槽位一样属于套餐权益；达到上限只阻止继续写入，不删除历史文件，管理员可按用户覆盖。

## 2. 为什么不再使用“总 Token / 1000”

当前实现将所有模型的 `prompt_tokens + completion_tokens` 相加后，按固定 Token 比例折算积分。这会产生四个问题：

- 不同模型每百万 Token 的供应商价格相差数倍甚至数十倍。
- 同一模型的输出 Token 通常明显贵于输入 Token，不能混成一个总数。
- 缓存命中输入往往比普通输入便宜，直接按普通 Token 收费不准确。
- 多模型任务目前只保存模型列表和合计 Token，无法追溯每个模型分别用了多少、按哪个费率结算。

Codex 和 Claude 的商业产品也没有把“一个原始 Token”直接承诺为固定使用权益。Codex 的可用量会随模型、任务复杂度、上下文、推理强度和工具使用变化，并允许在套餐额度外购买 credits；Claude 的 API 定价则明确区分输入、输出、缓存写入和缓存读取。这个项目应采用相同思路：套餐提供可理解的积分额度，后台把真实资源消耗换算成积分，而不是把积分伪装成 Token。

## 3. 积分定义

### 3.1 固定积分面值

定义：

> **1 积分 = ¥0.00216 的固定内部参考成本单位。**

该数值来源于最初采用的 DeepSeek Flash 峰值普通输入价格快照，即 `1,000 Token × ¥2.16 / 百万 Token`。来源只用于解释面值，不意味着积分以后永远绑定某个供应商、模型或 Token 数量。

积分是平台内部使用权益，不等于人民币、不可提现、不可转账，也不承诺与供应商 Token 一一对应。供应商调价时新增费率版本，不重新定义积分面值，不追溯修改余额或历史任务。

### 3.2 精确结算公式

每次任务按“模型调用明细”累计，任务结束后再统一向上取整：

```text
模型积分原值 =
    普通输入 Token × 输入权重
  + 缓存命中 Token × 缓存读取权重
  + 缓存写入 Token × 缓存写入权重
  + 输出 Token × 输出权重
  + 供应商明确单列的其他计费项

任务实际积分 = max(1, ceil(所有模型积分原值之和 / 1000))
```

为兼容现有“加权 Token 后除以 1,000”的实现形式，权重计算为：

```text
某计费项权重 = 该计费项人民币单价（元/百万 Token） / 2.16
某计费项积分 = Token 数 × 权重 / 1000
前台展示倍率 = 该计费项价格 / 基准快照价格
```

它与直接按人民币成本除以 `¥0.00216/积分` 完全等价；实现时以人民币成本和固定积分面值为最终依据，权重只是便于展示和兼容的派生值。

补充规则：

- 美元价格使用后台配置的汇率版本换算，首版测算汇率取 `1 USD = 7.20 CNY`，不是实时浮动汇率。
- 上下文阶梯价格按单次请求的实际输入长度选择对应档位。
- 如果供应商把推理 Token 包含在输出 Token 中，只计一次；只有供应商单独计价且未包含在输出用量中时才新增计费项。
- 缓存读取、缓存写入必须使用供应商真实返回的分类用量；若 Provider 无法可靠返回，发布费率时应明确采用普通输入价或禁止该模型进入真实计费，不能自行估算命中量。
- 按任务、按模型汇总后取整，不对每篇文献或每次小请求分别向上取整，避免大量碎片请求造成不合理放大。
- 无任何供应商计费用量的失败请求不扣积分；只要供应商已计费，就必须记录真实成本。
- 因平台协议解析、程序缺陷或证据校验实现错误造成的重试由平台承担；每次任务允许一次由平台承担的供应商瞬时故障自动重试；用户主动重跑或更换模型、方法、上下文后的重跑正常扣费。
- 每次尝试必须保存 `attempt_reason` 和承担方，不能在结算时根据日志文本反推。
- 管理员继续免扣积分，但必须完整记录等价积分和模型成本，便于经营核算。

## 4. 首版模型倍率

### 4.1 计算口径

费率不能只按“模型展示名称”配置。每条生产费率必须同时确定供应商、地域、服务档位、规范化模型及版本、上下文区间、输入/输出/缓存读写单价、币种、汇率版本和生效时间，并且只能追加新版本。

下表是截至 2026-10-14 再次核验后的公开标准价快照，对应生产费率版本 `credit-v2-2026-10-14-r2`。人民币模型采用中国大陆标准实时推理价；活动折扣、免费额度、DeepSeek 夜间优惠和 Batch 折扣不直接传导给用户，避免相同任务因调用时间不同而产生不可解释的差异。

“前台综合倍率”按平台典型初筛请求结构计算，并固定以 DeepSeek V4.1 Flash 峰值标准档作为 `1.0×`。倍率只是选型提示，统一四舍五入到最接近的 `0.25×`，低于 `0.25×` 的统一展示为 `0.25×`；最终扣费仍由任务实际调用的输入、输出和缓存用量按费率快照结算，不直接用展示倍率相乘。

| 平台模型与档位 | 公开标准价（输入 / 输出，元/百万 Token） | 前台综合倍率 |
|---|---:|---:|
| Qwen3.7-Flash ≤32K | ¥0.20 / ¥0.80 | 0.25× |
| DeepSeek V4.1 Flash 峰值标准档 | ¥2.00 / ¥8.00 | 1.0× |
| Qwen3.7-Plus ≤256K | ¥2.00 / ¥8.00 | 1.0× |
| Doubao Seed 2.1 Turbo | ¥3.00 / ¥15.00 | 1.5× |
| DeepSeek V4 Pro 峰值标准档 | ¥9.00 / ¥27.00 | 4.5× |
| Qwen3.7-Max | ¥12.00 / ¥36.00 | 6.0× |

注意：

- 平台继续接受历史 ID `deepseek-v4-flash`，但供应商请求和费率匹配统一落到规范化模型 `deepseek-flash`（当前展示名 DeepSeek V4.1 Flash）。
- DeepSeek 的非峰值优惠不进入首版用户计费，首版统一采用峰值标准费率，确保同一任务跨时段价格稳定。
- Qwen3.7-Flash 和 Qwen3.7-Plus 必须按单次请求上下文选择阶梯；显式缓存写入、缓存读取按供应商公开价格独立配置。
- Qwen Plus、Qwen Max、DeepSeek Pro 与 Doubao Seed 2.1 已完成真实调用、供应商模型 ID、服务档位和平台费率匹配验证；首版正式费率直接采用当前公开标准价。后续发现供应商价格变化时新增费率版本，不回写历史版本。
- 当前代码将缓存 Token 一律按普通输入价保守计算，只可用于旧账兼容或影子对比，不能作为新版真实结算实现。
- 费率快照 `ai-credit-v1` 仅是历史影子测算口径，不因本文直接升级为生产费率版本。
- 前端模型卡片显示“预计约 1.5× 积分”，任务确认页展示预计积分区间；用户账单和任务完成页只展示最终实际积分及按模型拆分的积分，不展示具体 Token 用量。Token 明细仅保留在后台审计数据中。

### 4.2 示例

假设某次任务使用 `1,500` 普通输入 Token 和 `300` 输出 Token：

```text
DeepSeek V4.1 Flash：
(1500 × 0.926 + 300 × 3.704) / 1000 ≈ 2.50 → 任务汇总后参与取整

Qwen3.7-Flash（≤32K）：
(1500 × 0.0926 + 300 × 0.3704) / 1000 ≈ 0.25
```

如果一个任务包含 100 篇文献，应先汇总 100 篇以及所有重试的实际用量，最后只进行一次向上取整。

## 5. 标准工作量积分测算

### 5.1 测算目标

用以下工作量作为一个“标准月度项目预算单元”：

- 2,000 篇文献；
- 使用 DeepSeek V4 Flash + Qwen3.7-Flash 双模型完成 AI 初筛；
- 其中 100 篇文献继续使用相同双模型完成 AI 质量评价。

### 5.2 样本依据

本次额度不是仅根据 Prompt 字符数估算，而是结合初筛历史任务与一次真实长全文质量评价基准确定：

| 环节 | 样本 | 实测口径 | 说明 |
|---|---:|---|---|
| AI 初筛 | 974 篇双模型任务 | 每篇每模型平均输入约 3,700、输出约 60 Token | 采用 2026-10-08 最新任务，已包含当前初筛 Prompt |
| AI 质量评价（旧链路） | 6 篇单模型任务 | 每篇每模型平均输入约 4,866、输出约 1,590 Token | 仅作历史对照，不再用于新版额度定案 |
| AI 质量评价（新链路真实基准） | 30 篇 QUADAS-2 全文、DeepSeek + Qwen 双模型 | 30/30 文献完成，240/240 次领域调用完成，实际总 Token 2,196,911 | 完整提取、按领域检索，没有提取截断；仅执行了这一次外部基准 |

#### 基准暴露的质量风险

模型调用和 JSON 解析均未失败，但证据校验并未全部通过：DeepSeek 出现 146 条引文匹配告警，Qwen 出现 215 条引文匹配告警和 9 条页码告警，并且两个模型的 30 篇文献都至少出现一条告警。

这不影响本次 Token/成本基准的有效性，因为供应商用量已经真实产生并完整记录；但它说明当前模型生成的直接引文与本地证据块之间仍存在系统性偏差。Prompt、引文约束和模型评价准确率属于后续独立调优专项，不阻塞本次计费功能重构。计费侧只需保证平台缺陷或校验策略造成的重试不转嫁给用户，并禁止无限自动重试；不再重复发送这批 PDF 做第二次基准。

### 5.3 计算过程

DeepSeek V4 Flash 的输入、输出权重分别为 `1.0` 和 `4.0`；Qwen3.7-Flash 的输入、输出权重分别为 `0.0926` 和 `0.3704`。

AI 初筛：

```text
DeepSeek 每篇 = (3,700 × 1.0 + 60 × 4.0) / 1000
               ≈ 3.940 积分

Qwen 每篇     = (3,700 × 0.0926 + 60 × 0.3704) / 1000
               ≈ 0.365 积分

2,000 篇双模型初筛 ≈ (3.940 + 0.365) × 2,000
                   ≈ 8,607 积分
```

AI 质量评价（当前 V2 链路复核）：

```text
5 篇双模型质量评价保守影子值 = 239 积分
每篇样本 P75                  = 53.47 积分
100 篇额度预算采用 P75        = 53.47 × 100
                              = 5,347 积分
```

合计：

```text
2,000 篇双模型初筛 = 8,607 积分
100 篇双模型质量评价（P75） = 5,347 积分
核心工作量合计 = 13,954 积分
增加 30% 的篇幅、输出、正常波动与计量误差余量 = 18,141 积分
标准月度项目预算单元取整 = 18,000 积分
```

这里的 18,000 积分是容量规划基准，不是对用户承诺的固定篇数。研究方法、全文长度、输出长度、模型组合、上下文阶梯和用户主动复跑都会改变实际消耗。

### 5.4 额度建议

首版月度积分定为：

| 套餐 | 月度积分 | 约合标准预算单元 | 设计含义 |
|---|---:|---:|---|
| Lite | 20,000 | 1.1 | 覆盖约一个标准工作量项目并保留少量余量 |
| Plus | 50,000 | 2.8 | 支持多个项目或更多复跑 |
| Pro | 120,000 | 6.7 | 支持高频处理和较多并行项目，同时控制成本边界 |

“约合标准预算单元”只用于内部容量判断，前台不宣传“保证处理 N 篇”。首发后继续记录至少 30 天真实账单；如果实际 P75 明显偏离本次样本，应通过下一商品版本调整额度，不追溯减少已经发放的积分。

## 6. 套餐设计

- 已有免费用户项目数超过 1 个时不删除、不锁定、不影响查看和导出，只禁止继续新建；确有测试或运营需要时通过管理员显式覆盖，而不是提高全部免费账户默认值。

按当前样本粗略估算，200 积分可支持约 46 篇 DeepSeek + Qwen 双模型初筛，或约 4 篇当前 V2 双模型质量评价；这只是体验量级，不是固定篇数承诺。

### 6.5 项目数量口径

- 项目上限指当前账户下尚未删除、仍可访问的项目总数，不按筛选项目和质量评价项目分别计算。
- 达到上限后禁止新建项目，但不影响查看、执行和导出现有项目。
- 用户降档或套餐过期后，如果已有项目数超过新上限，不自动删除或锁定历史项目，只禁止继续新建，直到数量低于上限。
- 删除项目属于不可逆数据操作，不能为了腾出名额自动执行；必须继续由用户明确确认。

### 6.6 并发与存储口径

- 套餐并发是“同一用户所有运行中任务合计正在占用的供应商调用槽位”。一个双模型任务可同时占用多个槽位；任务排队不占用调用槽位。
- 限制应由 Redis 原子计数或信号量实现，并包含用户、任务和系统全局三个层级；任务结束、超时和 Worker 异常后必须可回收。
- 首版不再单独销售“可同时运行 N 个任务”，也不通过套餐队列权重制造不可解释的等待差异。
- 存储统计覆盖索引、质量评价 PDF、派生文本与分块、导出产物、普通项目文件和反馈图片；套餐降档或到期后不删除已有文件，超出新额度时仅禁止新增写入。
- 首发阶段所有账户继续使用统一的上传大小、文件数量和安全存储限制。差异化 GB 配额等到存储用量计量、删除回收、超额拦截和管理员审计全部完成后再发布。

### 6.7 套餐价值校验

按 `1 积分 = ¥0.00216` 的 DeepSeek V4 Flash 峰值输入基准成本估算，20,000 / 50,000 / 120,000 积分对应的供应商基准成本上限约为 ¥43.20 / ¥108 / ¥259.20，分别约占套餐价格的 10.8% / 18.0% / 28.8%。尚未计入服务器、文件存储、邮件、运维、失败重试、税费、客服和支付通道成本，因此三个档位仍保留了安全空间，并且高档位的单位积分价格逐级下降。

正式上线前应使用至少 30 天真实调用数据重新计算：

- 各模型调用占比；
- 每篇文献平均输入和输出 Token；
- 失败及自动重试率；
- 质量评价全文带来的长上下文成本；
- 单用户峰值并发和存储成本；
- 实际供应商账单与平台计算成本的误差。

如果 Pro 的供应商成本长期超过套餐实收金额的 35%，应优先调整下一价格版本的包含积分或模型费率，不能追溯扣除用户已获得的积分。

## 7. 兑换码开通与续费

### 7.1 兑换码商品化

现有兑换码不能再只有一个 `credits` 数字。计划新增：

```text
code_type       = PLAN | CREDIT | ADDON
plan_code       = LITE | PLUS | PRO | null
price_version   = 价格版本
valid_months    = 1
credit_amount   = 套餐积分
batch_no        = 发放批次
expires_at      = 兑换码本身失效时间
redeemed_by     = 使用用户
redeemed_at     = 使用时间
```

- `PLAN` 码开通或续费套餐并发放一个积分批次。
- `CREDIT` 码只补充积分，用于售后补偿、活动或未来单独积分包，不改变套餐等级。
- `ADDON` 码关联已发布加购商品版本；订阅积分包和并发包要求兑换时有有效套餐，追加体验无需套餐。旧 `CREDIT` 码保留原规则，不套用新商品门槛。
- 每个兑换码只能成功使用一次，数据库唯一约束和事务锁共同保证并发兑换不会重复发放。

### 7.2 续费和换档规则

- 当前没有生效套餐：兑换后立即开通一个自然月，并发放本周期月度积分。
- 同档续费：允许连续兑换并堆叠多个月份，在当前排期末尾逐月顺延；每个月度周期的积分只在该周期开始时生效，不能提前透支。
- 升档或降档：兑换后安排在当前周期结束时生效；首版不做按日补差、立即换档或剩余天数折算。
- 同一账户最多保留一个“不同档位”的待生效变更；已有换档排期时拒绝再次安排另一档位。同档续费月份不受此限制。
- 套餐过期：用户回到免费体验状态，历史项目和数据仍可查看、导出；新任务按免费状态权限执行。
- 兑换码输错、过期或不适用时不得产生任何账户变更。

首版采用上述简单规则，避免手工兑换场景引入复杂的补差价、退款和按日折算。接入自助支付后再增加订单级升级和退款规则。

## 8. 积分批次和消费顺序

当前单一 `balance` 无法表达套餐积分、赠送积分和不同有效期。需要增加积分批次账本：

| 批次类型 | 建议有效期 | 是否可退款 | 说明 |
|---|---:|---:|---|
| WELCOME | 沿用当前规则 | 否 | 注册体验赠送 |
| PLAN | 对应套餐月度周期结束 | 随套餐退款规则 | Lite / Plus / Pro 附带积分 |
| PURCHASED | 商品配置 | 视订单规则 | 为未来积分包预留 |
| PROMOTION | 活动配置 | 否 | 运营活动赠送 |
| COMPENSATION | 后台配置 | 否 | 故障或售后补偿 |
| LEGACY | 不早于迁移前规则 | 否 | 仅保留为未来外部存量迁移兼容；本次测试期切账不使用 |

消费顺序采用：

1. 最早过期的可用批次优先；
2. 到期日相同，先消耗不可退款积分；
3. 永久积分最后消耗；
4. 每次扣费记录具体消耗了哪些批次，退款时只反向恢复原批次，不凭空生成新积分。

积分过期必须生成账本流水，不直接静默修改余额。用户余额等于所有有效批次剩余量之和，缓存余额只作为加速字段，可以由账本重建。

如果套餐批次到期时仍有积分被运行中任务预占，该预占继续保留到任务终态；最终未消费部分应直接记为到期，不再释放回可用余额。因平台故障需要补偿时，新建 `COMPENSATION` 批次，不复活已过期批次。

## 9. 预估、预占和最终结算

为了避免用户同时启动多个任务导致余额穿透，采用三段式流程：

```text
预估 → 原子预占 → 实际结算
```

1. **预估**：按文献抽样、Prompt 模板、模型费率和历史 P95 输出长度给出预计区间。
2. **预占**：任务创建时在事务内锁定账户和批次，将预计上限从“可用余额”移入“冻结余额”。
3. **执行**：逐次记录每个模型调用的输入、缓存、输出、重试和供应商请求 ID。
4. **结算**：任务结束后按创建时冻结的费率版本计算实际积分，多余冻结额度释放，实际不足部分优先从其他有效批次补扣；模型已经调用而余额仍不足时不制造负余额，差额明确记为平台承担。
5. **异常恢复**：任务失败或取消时仍结算供应商已经产生的真实用量，其余冻结额度释放；结算操作必须幂等。

若预占跨越积分批次到期时间，“释放”必须先判断批次是否仍有效：有效批次恢复为可用，已到期批次转为过期流水。任务不能利用长时间运行把已过期积分重新变成可用积分。

当余额不足以完成预占时，不启动任务，并向用户展示“预计需要、当前可用、不同模型预计消耗”而不是笼统提示余额不足。

费率在任务创建时冻结。即使管理员在任务运行期间发布新费率，这个任务也继续使用旧版本，保证可解释性。

## 10. 数据模型建议

建议在现有账户和流水基础上增量扩展，不替换 Django User：

| 模型 | 作用 |
|---|---|
| `PlanCatalog` | Lite / Plus / Pro 的稳定产品标识 |
| `PlanPriceVersion` | 价格、有效月数、包含积分、并发、项目上限及生效时间 |
| `UserPlanEntitlement` | 用户当前套餐、开始/到期时间、来源兑换码或订单 |
| `PlanBillingPeriod` | 每个自然月周期、当期权益快照和月度积分发放状态，用于幂等补发与追溯 |
| `CreditGrantBatch` | 每笔积分来源、总量、剩余量和到期时间 |
| `CreditTransaction` | 保留总账流水，并关联批次明细、任务和幂等键 |
| `CreditAllocation` | 一次消费跨多个积分批次时的分摊明细 |
| `ModelBillingRate` | 供应商、规范化模型版本、地区、服务档位、币种、汇率、输入/输出/缓存权重、上下文阶梯和版本 |
| `ModelUsageDetail` | 每次模型调用的 Token 分类、请求 ID、上下文档位、尝试原因、承担方、费率版本和积分结果 |
| `CreditReservation` | 任务预占、释放、结算和状态机 |
| `RechargeCode` | 扩展套餐、价格版本、积分、有效月数和批次字段 |

关键约束：

- 费率、价格和权益都只新增版本，不原地修改历史快照。
- `ModelUsageDetail` 必须使用平台规范化模型 ID；旧模型别名在请求路由后再落规范化 ID。
- 计费明细只关联现有任务、质量评价运行和信号结果，不复制业务结果正文，避免出现第二套评价数据源。
- 兑换、预占、结算、退款都使用唯一幂等键。
- 余额、冻结余额、批次剩余额度的更新均使用数据库事务和行锁。
- 月度发放使用 `entitlement_id + period_start` 唯一约束；定时任务与登录、兑换、创建任务时的按需校正共用同一幂等逻辑，不能只依赖 Celery Beat。
- 权益解析优先级固定为：管理员显式覆盖（可空）> 当前生效套餐 > 免费默认值。套餐权益不复制写入多个用户字段，避免后续漂移。
- 用户、任务、项目、兑换码和交易的关联必须保持租户隔离，普通用户只能查看自己的账单明细。

- 所有 Provider 返回供应商、地域、服务档位、规范化模型及版本、输入 Token、输出 Token、缓存读写 Token、供应商请求 ID、调用次数和重试序号。
- 每次调用记录实际请求上下文长度及命中的价格阶梯，不能只保存一篇文献的合计 Token。
- 区分 API 调用失败、模型输出解析失败、本地证据校验失败、平台自动重试和用户主动重跑，并保存 `attempt_reason` 与承担方。
- 修正 V2 报告 JSON、Provider 返回和最终 `TokenUsageLog` 的缓存数量冲突，任务汇总只能由逐调用明细聚合得到。
- 未识别模型必须完整落审计记录并阻止真实扣费，不能猜一个倍率继续结算。

**验收门槛：**双模型任务的逐调用明细之和等于任务总量；现有筛选和质量评价结果不受影响。

### 阶段 3：版本化积分计算器（已完成本地实现）

- 使用 `Decimal` 和固定 `¥0.00216/积分` 实现输入、输出、缓存和长上下文阶梯的纯函数计算器。
- 费率在任务创建时冻结，结算时引用快照；历史结果可重复计算。
- 所有调用先汇总原值，任务级只向上取整一次。
- 管理员免实际扣费，但仍计算并保存等价积分和人民币成本。
- 平台自身校验缺陷触发的自动重试默认由平台承担；用户主动重跑正常计费。具体分类必须进入明细，不能仅靠日志判断。

**验收门槛：**同时回放 30 篇历史基准与 5 篇当前 V2 数据；历史 `1,289` 和当前保守 `239` 只作为解释差异的参照，最终结果必须以归一化后的逐调用缓存口径为准。覆盖阶梯边界、缓存、未知模型、任务级舍入和汇率版本单元测试。

### 阶段 4：测试期积分账本初始化（已完成实现、人工初始化与对账）

- 平台尚未对外开放且没有真实付费权益，因此不迁移旧余额，也不为旧流水构造 `LEGACY` 批次。
- 提供一次性、强确认的 `initialize_credit_v2` 命令：清理旧积分流水/批次/预占，将普通有效账户统一初始化为 200 欢迎积分，管理员保持 0 且继续免扣费。
- 初始化只允许人工执行，不能放入自动数据库迁移；重复执行必须被拒绝，未使用旧兑换码统一作废。
- 实现最早到期优先消费、跨批次分摊、到期流水、原批次退款和只读账本核对命令。
- `CREDIT` 兑换码创建独立 `PURCHASED` 批次并使用行锁保证并发只能核销一次；`PLAN` 兑换码留到阶段 7。
- 过期批次上的未消费预占直接过期；平台补偿创建新 `COMPENSATION` 批次，不复活旧批次。

**验收门槛：**人工初始化后全量账实核对为零差异；并发消费不会出现批次负数；重复初始化不会重复发放；旧兑换码不能再次兑换。

测试环境切账顺序：

```bash
python manage.py migrate
python manage.py initialize_credit_v2 --dry-run
# 进入维护模式并完成数据库备份后执行：
python manage.py initialize_credit_v2 --initial-credits 200 --confirm RESET-CREDIT-V2
python manage.py reconcile_credit_ledger --fail-on-difference
```

确认核对无差异后才能设置 `CREDIT_BATCH_LEDGER_ENABLED=true`。到期任务可定时执行
`python manage.py process_credit_expirations --apply`；不传 `--apply` 时只预览。

### 阶段 5：模型感知预估、预占与结算状态机（已完成并在本地开启）

- 任务启动前给出预计区间并在事务中原子预占。
- 执行结束按真实用量结算，多余预占释放，不足部分按规则补扣。
- 失败、取消、超时、Celery 重投和重复回调都通过幂等键处理。
- 对同一用户并发启动任务进行行锁和竞争测试，避免余额穿透。
- 覆盖套餐周期结束时仍在运行的任务，确保预占既不丢失也不会在释放后绕过到期规则。
- 初筛不再按每篇每模型固定 2 积分：使用当前费率版本、3,700 输入 / 60 输出 Token 基准及 30% 波动余量，按所选模型动态计算。
- 质量评价使用四领域调用基准、每调用约 5,000 输入 / 100 输出 Token 和 25% 波动余量；DeepSeek 基准仍约等于每篇每模型 27 积分。
- 预估接口同时返回各模型单篇积分、相对最低成本模型的倍率、基础预估与预占上限；最终结算仍以真实分类用量为准。
- AI 初筛与 AI 质量评价的模型选择区均展示相对倍率，并会随文献范围和模型选择实时更新“基础预估～预占上限”；余额不足时前端禁用启动，后端仍执行最终预检。
- 实际用量超过预占时先补扣当前有效批次；调用已经发生但余额仍不足的部分记录为平台承担，禁止产生负余额。

**验收门槛：**重复结算只扣一次；所有终态冻结余额归零；余额不足时模型调用不会启动。

### 阶段 6：统一权益与用户聚合并发（已完成本地实现）

- 建立单一权益服务，解析优先级为管理员显式覆盖 > 当前套餐 > 免费默认值。
- 将 4 / 8 / 16 实现为用户跨任务聚合的供应商调用槽位，并同时受任务级与系统全局上限控制。
- 项目创建统一使用权益服务校验；免费账户默认 1 个项目，超额存量只限制新增。
- 修正管理员表单和字段校验，使 Pro 的 16 槽位可配置；实现 Redis 槽位超时、异常退出回收和数据库兜底审计。
- 将存储纳入统一权益：免费 5 GB，Lite / Plus / Pro 分别为 20 / 50 / 100 GB，并支持管理员单用户覆盖。

实现结果：

- 权益统一由 `entitlement_service` 解析，不再直接把旧 `UserProfile` 配额字段作为新版依据。
- 免费账户默认 1 个项目、2 个槽位和 5 GB；Lite / Plus / Pro 分别为 5/10/20 个项目、4/8/16 个槽位和 20/50/100 GB。
- Redis 使用带 TTL 的任务租约，同时检查系统全局上限和同一用户跨任务聚合上限；AI 初筛和质量评价共用槽位池。
- 运行租约和排队记录均设置独立 TTL；Worker 或 Celery 重试记录丢失后不会永久占槽或堵塞队首。
- 任务配置保存权益和槽位快照；Redis/Worker 异常后租约自动到期，管理员仍可执行运维重置。

**验收门槛：**同一用户的多个任务合计不会超过权益槽位；Redis/Worker 异常后不会永久占槽；免费权益不优于 Lite；管理员覆盖可撤销并立即回落到套餐或免费默认值。

## 14. 验收标准

1. 同样 Token 用量选择不同模型，会按费率版本产生不同且可复算的积分。
2. 输入、输出、缓存和长上下文阶梯均能独立计价。
3. 多模型任务可以逐模型追踪用量，分项之和等于最终账单。
4. 同一兑换码并发提交只能有一次成功，积分和套餐均只发放一次。
5. 同一任务重复结算不会重复扣费。
6. 多个并发任务不能共同花掉同一份可用积分。
7. 失败、取消、重试和超时均能正确结算真实用量并释放剩余冻结额度。
8. 费率发布后不改变历史任务、历史流水和运行中任务的计算结果。
9. 测试期切账后普通有效账户统一获得 200 欢迎积分，管理员为 0 且免扣费；历史项目不受积分初始化影响。
10. 普通用户只能查看自己的套餐与账单，管理员能查看全局成本和核销审计。
11. 免费账户默认 1 个项目、2 个用户聚合调用槽位；Lite / Plus / Pro 分别为 4 / 8 / 16，且多个活动任务共享同一用户上限。
12. 同档套餐可连续续费多个月，但不同档位只允许一个未来变更；每个周期积分只发放一次。
13. 跨积分到期时间运行的任务不会丢失预占，也不会把已过期积分重新释放为可用余额。
14. 5 篇当前 V2 样本的报告、逐调用明细、任务汇总和影子账单可以完成一致性核对。

## 15. 暂不实施的内容

- 微信、支付宝自助支付及自动续费；
- 年付折扣套餐和按日补差价升级；
- 团队空间、席位、共享积分池；
- 积分转赠、提现或用户之间交易；
- 动态夜间折扣、供应商促销价实时传导；
- 基于单个用户议价的个性化费率。
- Prompt、引文匹配和 AI 评价准确率专项调优；其结果以后通过真实用量自然反映到新费率和额度复盘中。

这些能力可以在当前数据模型上继续扩展，但不应进入首版，以免兑换码试运营阶段就承担完整支付和订阅系统的复杂度。
