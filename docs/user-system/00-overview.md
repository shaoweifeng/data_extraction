# 用户体系与 AI 筛选计费改造 · 整体方案

> 本文件为整体方案总览。各阶段的详细落地计划见同目录下 `01-phase1.md` ~ `06-phase6.md`。

## 背景与目标

当前平台已有 Session 认证、UserProfile/RBAC 权限、AI 筛选异步（Celery）执行框架，但存在：

- 注册强制审核，且注册时不自动创建 `UserProfile`；
- AI 筛选并发写死 16，且无全局上限——多任务线程叠加会打满服务器（2c2G）；
- 无额度/计费体系；
- 无个人中心。

本方案实现 6 项能力：自主注册登录、用户分级、免费额度与 token 计费、付费充值、个人中心、并发控制。

## 关键决策（已与用户确认）

| # | 决策 | 取值 |
|---|---|---|
| 1 | 审核 | **免审核**；`is_banned` 作封禁开关，默认可用 |
| 2 | 计费单位 | **1 credit = 1000 tokens**（`CREDIT_TOKEN_RATIO` 可配） |
| 3 | 免费额度 | 注册赠送 **200 credits**（≈100 篇，一次性） |
| 4 | 预扣策略 | **直接扣、多退少补**；启动前预估不足则拒绝 |
| 5 | 全局并发上限 K | **50**（Redis 信号量控制 AI 请求总并发） |
| 6 | 用户档位 | 普通=**2**，充值可升 4/8 |
| 7 | 充值 | **手动**（兑换码 / 管理员充值），暂不接支付 |
| 8 | 防白嫖 | 必做：同 IP 限流(24h≤3)+小额赠送；可选：邮箱验证(开关默认关) |

## 核心机制：计费 + 并发「双层闸门」

```
用户启动 AI 筛选
  → [预估] N 篇 × 单篇均值(ESTIMATE_CREDITS_PER_REF) → 余额校验，不足则 402 拒绝
  → [预扣] 直接扣预估额度，写 consume 流水
  → [派发] Celery 任务入 screen 队列（worker_concurrency 限制同时执行任务数 = 第1层闸门）
  → [执行] 每批请求前 acquire Redis 全局信号量(≤K=50)，请求后 release（= 第2层闸门）
  → [采集] 每批解析 usage.total_tokens，累加
  → [结算] 批次/任务结束按真实 token 计费，多退少补，刷新余额
  → [明细] 写 TokenUsageLog
```

## 数据模型（新增 5 张表）

```
User 1—1 UserProfile 1—1 CreditAccount 1—* CreditTransaction
User 1—* RechargeCode(兑换码)    User 1—* RegistrationLog(防白嫖)
Task 1—* TokenUsageLog
```

## 落地顺序与依赖

```
阶段一(认证/分级) → 阶段二(额度基建/采集) → 阶段三(计费接入)
                                    → 阶段四(并发控制, 依赖阶段一档位字段)
阶段五(防白嫖, 依赖阶段一注册) → 阶段六(个人中心/充值, 依赖阶段二三)
```

- 阶段一、二可先行且互相独立；三依赖二；四依赖一（档位字段）与二（可选）；五依赖一；六依赖二三。
- 每阶段结束都能独立验证、可上线，不破坏现有筛选主流程（阶段二为纯旁路记录）。

## 全局风险与注意事项

1. **迁移安全**：role 收敛与新表迁移需写数据迁移脚本；先备份 MySQL。
2. **usage 缺失兜底**：部分模型/mock 无 usage 时，按篇数估算兜底计费，避免免费漏计。
3. **Redis 信号量泄漏**：请求异常必须 `finally release`；加 TTL 兜底防止计数只增不减。
4. **并发与档位反推**：worker_concurrency × 最大档位应 ≤ K，避免第1层放过量任务后在第2层大量阻塞。
5. **计费一致性**：扣费/结算用 `select_for_update` 或原子 `F()` 更新，防并发竞态导致余额错乱。
6. **预扣误差**：单篇均值 `ESTIMATE_CREDITS_PER_REF` 需根据阶段二采集的真实数据校准（先取 2，上线后调整）。
