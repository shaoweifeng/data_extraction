## 一、结果查询性能改造

### 已定位问题

1. AI 初筛页面会以每页 200 条预加载最多 1000 条已筛结果，并可能在进度变化时重复刷新整批结果。
2. `/api/review/list/` 的分页发生在 Python 全量加载、过滤、排序之后；每个分页请求都会重新打开并解析项目的全部结果 JSON。
3. `/api/review/stats/` 会独立再次读取全部结果 JSON，与列表请求重复工作。
4. 当前旧实现按每条记录递归扫描项目目录查找 XML；重构分支已改成单次批量扫描，但仍未建立稳定索引。
5. 列表响应携带摘要和多模型明细，200 条时单页可达到约 1.1–1.4 MB。
6. 项目切换的 generation 校验只能阻止旧响应污染页面，不能取消已经发出的重型请求。

### 2026-09-08 已直接完成

- AI 初筛已筛列表改为每页 50 条、点击时按需请求，不再首屏预取最多 1000 条。
- AI 任务运行中的轮询只刷新进度和轻量统计；待筛/已筛列表仅在任务完成或停止时统一刷新。
- 待筛列表、已筛列表和统计请求已支持 `AbortController`；新请求会取消同类旧请求，组件卸载时会取消未完成请求。
- 后端 `/api/review/list/` 仍会先加载全量 JSON 再分页；这一根本瓶颈需先确认结构化结果模型。

### 现有证据

- 项目 50 包含 772 个 JSON、1841 个 XML，共 2617 个文件。
- 日志中约 27 秒内多次重复请求第 1–4 页，每页 200 条，存在明显请求放大。
- 约 772 条结果时，一次 AI 初筛页面初始化可能触发约 `4 × 772 + 1 × 772 ≈ 3860` 次 JSON 打开和解析，重复刷新会继续倍增。
- 人工审阅首屏虽然只显示 30 条，但列表和统计仍可能合计读取约 `2 × 772` 个 JSON。

### 推荐方案

1. 建立可查询的结构化结果索引，推荐使用数据库表保存文献基础字段、AI 决策、人工决策、状态和排序字段；单篇 XML/JSON 保留为兼容导出或审计产物，不再作为页面查询主数据源。
2. 列表接口在数据库层完成项目过滤、状态过滤、搜索、排序和分页，只查询当前页。
3. 统计在任务写入结果时增量维护，或按项目/结果版本缓存；结果变化后精确失效，不在每次页面打开时扫描全部文件。
4. 列表只返回标题、作者、年份、决策、简短原因等展示字段；摘要和多模型明细通过详情接口按需读取。
5. AI 初筛页面只加载当前可见页。任务运行中只轮询轻量进度和计数，完成时刷新一次列表。
6. 对相同项目、相同查询参数的请求做合并，并在组件卸载、项目切换或新请求替代旧请求时取消旧 HTTP 请求。
7. 在过渡期至少建立 `source_xml → 文件路径` 的一次性索引，禁止逐条 `rglob()`。

### 验收标准

- 1000、5000、10000 条文献下，列表请求的文件读取次数和返回体大小只随 `page_size` 增长，不随项目总量线性增长。
- 页面初始化不再自动抓取全部结果；同一轮刷新不存在相同分页的重叠请求。
- 1000 条项目的首屏列表响应建议控制在 1 秒级，具体阈值在基线阶段按服务器硬件确认。
- 统计接口不读取单篇结果 JSON，不出现按文献数量增长的 SQL N+1。
- 项目切换后旧请求被取消，且不会继续占用后端工作线程。

## 二、文献索引上传与解析内存改造

### 结论（已部分改造）

原重构没有修复索引解析的内存放大。2026-09-08 已完成一批不涉及业务决策的改造：

1. `ParseHandler` 通过 `iter_directory()` 按文件消费记录，并在同一遍中写合并 XML 和单篇 XML，不再为后续拆分阶段保留全项目 `entries`。
2. `convert_to_xml()` 改为逐条写出，删除 `ElementTree → tostring → minidom → splitlines → join` 的整文档副本链。
3. NBIB/Medline 改为单遍逐行状态机；ENW/TXT 使用固定 64 KB 块检测编码并逐行解析；CIW 不再先累积全部原始记录。
4. XML 改为 `iterparse()`，标准化每条记录后立即 `elem.clear()`。
5. RIS、BibTeX 和 DOC/DOCX 仍受第三方库全量加载限制，单个大文件的内存仍会随条目数增长。解析任务并发限制和文件上限仍待确认。

HTTP 上传本身通过 Django `FileField` 保存，前端也没有把文件转为 Base64 或主动复制成字符串。当前最明显的内存问题发生在**上传完成后触发的解析任务**，而不是浏览器上传进度逻辑。项目没有显式设置 Django 上传内存阈值，仍依赖框架默认行为，后续应将阈值显式化，但它不是主要放大源。

### 各格式风险

| 格式 | 当前行为 | 风险 |
| --- | --- | --- |
| RIS | `rispy.load()` 先构造全部原始记录，再生成全部标准化记录 | 高 |
| NBIB/Medline | 已改为单遍逐行状态机 | 低（输出仍随条目数增长） |
| ENW/TXT | 已改为分块编码检测和逐行解析 | 低（输出仍随条目数增长） |
| XML | 已使用 `iterparse()` 并及时释放记录节点 | 低（输出仍随条目数增长） |
| BibTeX | 第三方库加载完整文献库，再复制成标准化列表 | 中高 |
| CIW | 已逐条标准化，不再保留原始 records 副本 | 低（输出仍随条目数增长） |
| DOC/DOCX | python-docx 加载文档对象，随后再构造 lines、full_text、原始记录和标准化记录 | 高 |

### 本地隔离基准

以下数据仅用于证明放大路径，不能替代服务器基线：

| 输入 | 条目数 | 输入大小 | Python 跟踪峰值 | 进程峰值 RSS |
| --- | ---: | ---: | ---: | ---: |
| RIS | 1162 | 5.5 MB | 79.1 MB | 128.7 MB |
| ENW | 500 | 2.0 MB | 18.5 MB | 53.6 MB |

改造后使用同一 ENW 样本执行“解析 + 合并 XML”，Python 跟踪峰值为 **2.48 MB**（原为 18.5 MB，降低约 86.6%）。之前仅将 XML 输出流式化时，RIS 样本 Python 跟踪峰值由 79.1 MB 降至 13.1 MB；RIS 解析器本身的全量加载仍需后续改造。

基准只执行了解析和合并 XML 生成；实际 Worker 还包含 Django/Celery 基线内存、拆分文件保存、数据库对象和并发任务。因此线上峰值会更高。

### 推荐方案

1. 将解析器统一为迭代器协议，例如逐条产生标准化 `ReferenceRecord`，不再返回全量 `List[Dict]`。
2. 采用单遍流水线：读取一条记录后立即校验、写入结构化索引、写单篇产物，并追加到流式合并 XML；内存中只保留当前记录和小批次缓冲。
3. 合并 XML 使用流式 writer，删除 `ElementTree → tostring → minidom → splitlines → join` 的整文档格式化链路。
4. NBIB、ENW/TXT、CIW 改为逐行状态机；XML 使用 `iterparse()` 并及时 `elem.clear()`；RIS 优先使用迭代解析或实现兼容的逐记录状态机。
5. BibTeX、DOCX 若受第三方库限制，先采用独立任务、文件大小/条目上限和明确错误提示，再评估流式替代实现。
6. 数据库记录使用固定小批次 `bulk_create`，避免逐篇 ORM 写入，同时保持批次内存上限。
7. 输出先写任务临时目录，全部成功后再原子替换正式产物；失败时保留旧结果，保证流式化不破坏当前重跑语义。
8. 显式配置 Django 上传内存阈值和单文件大小限制，使大文件稳定落临时磁盘；配置值结合服务器内存和并发度确定。
9. 为解析任务设置独立并发上限。不能沿用适合网络型 AI 请求的 16 线程并发度直接承载多个大文件解析任务。

### 验收标准

- 对可流式格式，峰值 Python 分配不随总条目数线性增长；以固定小批次大小为主要上限。
- 在 1000、5000、10000 条基准数据上记录耗时、峰值 RSS、产物条数和字段一致性。
- 同一 Worker 并发执行允许数量的最大样本时，不触发 OOM，也不显著挤压 Web 进程。
- 新旧解析输出进行字段级对比，标题、作者、年份、摘要、DOI、URL、来源文件和来源位置保持一致。
- 中途失败或停止不会发布半套新结果，也不会提前清除上一版有效产物。

## 三、建议实施顺序

### Performance Phase 0：基线与保护

- 为结果列表、统计、解析任务增加耗时、SQL 数、文件读取数、响应大小和峰值 RSS 基线。
- 建立 1000/5000/10000 条合成数据及真实格式样本。
- 添加结果一致性与内存/查询复杂度回归测试。
- 明确上传大小限制、解析任务并发限制及失败行为。

### Performance Phase 1：流式导入

- 定义统一 `ReferenceRecord` 和迭代解析协议。
- 优先改造 NBIB、ENW/TXT、CIW、XML、RIS。
- 实现流式合并 XML、单篇产物输出和批量索引写入。
- 单独评估 BibTeX、DOC/DOCX 的第三方库限制。

当前进度：流式 Handler/输出、NBIB、ENW/TXT、CIW、XML 已完成；RIS、BibTeX、DOC/DOCX 待后续评估。

### Performance Phase 2：可查询结果模型

- 设计文献、AI 判断、人工判断的数据表或等价持久化索引。
- 在解析和 AI 筛选阶段增量写入索引。
- 提供数据库级分页、筛选、搜索、排序和统计。
- 如需兼容既有项目，增加可重复执行、可校验的回填流程。

### Performance Phase 3：前端按需加载

- AI 初筛和人工审阅改为真正的服务端分页。
- 运行中只刷新轻量进度；合并重复请求并取消过期请求。
- 摘要、多模型明细改为展开或详情时加载。

当前进度：AI 初筛的按需分页、运行期轻量轮询和请求取消已完成；人工审阅的数据库级分页及详情字段拆分待结果模型确认。

### Performance Phase 4：兼容层清理与联调

- 对比新旧结果数量、字段、AI 判断和人工审阅状态。
- 完成大项目、多项目并发、任务停止/重试和项目切换联调。
- 确认所有消费者切换后，移除运行时全量 JSON/XML 扫描路径；保留用户需要的下载和审计产物。
