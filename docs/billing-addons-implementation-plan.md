## 2. 已确定的业务规则

### 2.1 订阅资格与积分

1. 订阅积分包和并发包在兑换生效时要求存在当前有效的个人套餐；历史订阅、已到期套餐及仅有未来待生效套餐均不满足条件。
2. 前端显示资格，后端事务内重新校验；资格不足不能消耗兑换码，也不能产生积分或权益记录。
3. 追加体验积分无需套餐，不提高项目、存储和并发。免费注册赠送的既有规则保持不变。
4. 追加体验按份提供，每份 5,000 积分；首版一份对应一个码，批量发码表示多份，不引入前端购物车或数量结算。
5. 有套餐的用户也可兑换追加体验码；页面优先展示更优惠的订阅积分包。
6. 新商品积分从兑换成功起有效 12 个自然月，分别生成批次；套餐随后到期不提前作废这些积分。
7. 兑换码失效时间与积分批次失效时间独立。先到期先消费、任务预占、实际结算和释放均复用现有账本。
8. 积分过期但仍被任务预占时，按现有账本规则完成结算；释放时不能把过期额度重新变成可用余额。
9. 售后补偿、活动积分和旧积分码不自动套用新商品的套餐门槛或有效期，保留原语义，后台明确区分来源。

### 2.2 并发升级

1. 并发包为“提升至目标档位”，不按加法叠加；同一账户全部项目、初筛和质量评价任务共享。
2. 普通账户有效并发为 `max(套餐/免费基础并发, 当前有效并发包目标)`；管理员覆盖拥有最高优先级，researcher 仍按普通权益计算。
3. 首次兑换立即生效一个自然月；有效期使用左闭右开区间，存储 UTC、展示账户时间，并复用现有自然月锚点规则。
4. 同档续期顺延一个自然月；首版不支持有效期内跨档兑换，不做按日补差或折算。
5. 新开并发包的目标须高于当前基础并发；同档续期也须仍然有提升价值。资格校验不能误把当前包带来的并发视作基础并发。
6. 套餐中途升级后取较大值，包不退款、不暂停、不延长；到期后回落到当时基础权益。
7. 套餐到期后，已兑换的并发包持续至自身到期；无有效套餐时不能新增兑换或续期。
8. 降档不终止已发出的模型请求；已有槽位自然释放，新请求按最新上限申请，不能先删除活动槽位来强制满足新上限。
9. 供应商与平台全局限流继续生效，不承诺速度等比例提升。
10. 当前 Lite/Plus/Pro 基础并发为 4/8/16，因此“4 并发包”没有符合资格的现有套餐用户。保留其商品配置但默认不上架；Lite 可选 8/16，Plus 可选 16，Pro 暂无更高档可选。

## 3. 当前代码基础与缺口

- `RechargeCode` 已有 `CREDIT/PLAN`，但积分码尚无独立积分包商品关联及商品资格校验。
- `redeem_credit_code` 已使用批次账本，当前发放 `PURCHASED`，未为商品积分传入到期时间，需要区分新商品码与旧通用码。
- `CreditGrantBatch` 已支持过期、预占和来源；优先复用，通过关联商品版本和发放来源补足追溯，不重复建立余额系统。
- `entitlement_service` 已统一解析套餐、免费及管理员覆盖；目前没有独立限时并发包，需要扩展此服务及相关返回值。
- `BillingView.vue` 已有套餐卡片、统一兑换入口、积分批次与联系方式入口，可扩展商品页签。

## 4. 实施阶段

### 阶段 0：冻结规则与代码边界

- 核对现有模型、兑换入口、Admin 发码、联系方式参数及初筛/质量评价槽位调用点。
- 将本文商品表和规则作为验收口径，标明 4 并发包暂不上架。
- 复用 `core/services`、既有 billing API 和 `web/src/features/billing` 的组织方式，不把发码、权益、账本逻辑塞进视图。

验证：列出受影响模块；确认没有在线支付或金额流水功能混入范围。

### 阶段 1：商品版本与数据库结构

- 新增积分包/体验包/并发包目录和不可变版本，包含稳定商品编码、展示名、参考价、积分数或目标并发、有效月数、订阅门槛、排序及上架状态。
- 套餐沿用现有目录，新增商品不强行重构套餐模型。
- 扩展兑换码商品关联及并发类型；商品码使用明确关联，不能靠金额、积分数量或备注猜测商品种类。
- 新增用户并发权益记录，记录用户、商品版本、起止时间、原始开通来源；续期保留每次兑换的独立审计关联。
- 积分发放记录保存可追溯的商品版本/来源；已有积分批次与通用码保持兼容。
- 通过**新增迁移**创建结构与初始商品数据，不修改已有迁移；商品发布后生成新版本而非覆盖历史版本。

验证：迁移检查；旧码可读取；初始商品数量、价额、有效期和订阅门槛正确；已发行码关联的历史版本不会被调价覆盖。

### 阶段 2：积分商品兑换与 Admin 发码

- Admin 按商品版本生成安全随机码，复用既有批次发码和审计。
- 新商品积分码兑换时，在同一事务内校验用户套餐、商品适用性、码有效性并发放带 12 个月有效期的积分批次。
- 统一锁顺序与现有套餐/积分流程协调，防止双击、跨用户抢兑、并行续费和多码兑换产生重复发放或死锁。
- 保留旧通用积分码及人工补偿入口，不把它们公开展示为可绕过订阅限制的商品。
- 正确识别商品下架与版本撤销：下架只停止新展示和发码，已发行有效码仍可兑换；明确撤销的版本才拒绝兑换并记录原因。

验证：免费/有效套餐/到期/待生效资格矩阵；同码并发仅成功一次；拒绝时码和余额不变；积分到期与套餐到期相互独立；旧码行为不变。

### 阶段 3：并发权益与运行时生效

- 新增并发码兑换服务，实现立即开通、同档续期、跨档拒绝和订阅校验。
- 在统一权益服务中计算基础并发、附加并发、最终并发及到期时间，不写入管理员 `ai_call_slots_override`。
- 检查初筛、质量评价、Redis 槽位、数据库兜底及任务本地并发窗口，避免只更新权益展示而运行任务仍使用旧值。
- 权益判断以实际时间为准，定时任务仅整理状态，不能依赖定时任务恰好执行才触发到期。
- 按现有锁和事务边界同步套餐状态，避免查询权益产生新的锁顺序问题。

验证：Lite→8/16、Plus→16；免费/Pro/无提升拒绝；续期与月末；多项目和双模型共享；包到期和套餐到期；运行任务升降档；管理员覆盖与 researcher 行为。

### 阶段 4：API、商城与联系方式联动

- 商城三个页签为“个人套餐”“积分补充”“并发升级”；积分补充中根据账户优先展示订阅积分包或追加体验。
- 无资格商品显示清晰提示和套餐入口；Pro 并发页显示“当前已为最高档”，不提供无效购买按钮。
- 联系方式弹窗携带商品名称、积分/并发及有效期，复用现有二维码查看与复制功能。
- 保留一个统一兑换入口；兑换后同步刷新积分余额、批次、套餐与最终并发。
- 展示并发构成，例如“套餐 4 · 升级至 8 · 有效至……”，避免用户误认为叠加为 12。
- 成本和毛利仅在内部方案/Admin 中展示；用户页面展示参考售价与可获得权益。
- 普通用户接口不能创建商品、任意积分或管理员覆盖，所有资格校验均在后端。

验证：三类账户页面；未配置联系方式的默认展示；移动端布局；二维码放大；失败和成功状态；服务器端绕过前端的直接兑换请求。

## 5. 人工验收重点

1. 免费账户能兑换 5,000 体验积分，不能兑换订阅积分包或并发包。
2. Lite 用户可兑换三个订阅积分包及 8/16 并发包；每份体验积分始终为 5,000。
3. Plus 不能兑换无提升的 8 并发包；Pro 没有可用并发升级商品。
4. 套餐到期后，独立积分和并发包按各自到期时间继续生效，但失去加购资格。
5. 兑换成功立即刷新权益，多任务实际共享新并发；到期降档不终止已有请求。
6. 旧码兼容、重复兑换保护、版本追溯和积分对账均正确。

## 6. 部署与 Admin 操作

### 6.1 部署

新增迁移为 `0048_addonproduct_alter_rechargecode_code_type_and_more`（结构）与 `0049_seed_billing_addons`（初始商品）。迁移不会清空积分或修改原套餐权益，也不会自动为用户兑换商品。

在项目目录、已激活虚拟环境后执行：

```bash
python manage.py migrate
./stop.sh
./start.sh -d
```

生产升级建议先暂停任务派发并等待活动任务结束，再迁移和重启。`start.sh -d` 会构建前端；如果由部署流水线构建，使用该流水线的正常部署步骤即可。Web 与 Worker 都须更新，避免商城新权益与旧 Worker 的运行时逻辑不一致。

无需新增 `.env` 参数；沿用已启用的 `PLAN_BILLING_ENABLED` 与 `CREDIT_BATCH_LEDGER_ENABLED`。

### 6.2 商品与发码

1. 在 Admin 的“加购商品”中调整上架状态和排序。4 并发商品默认下架。
2. 在“加购商品版本”查看已发布价额、有效期、资格、模型参考成本；调价时新增草稿版本，填写与目录一致的类型，选中草稿执行发布。
3. 同一商品商城只展示最新已发布版本。旧版本码继续按旧权益兑换；商品下架不使已发行码失效。误发的版本可通过“撤销所选商品版本”操作停用，已兑换权益继续有效。
4. 在“兑换码 → 批量生成”选择“加购商品码”，选择已发布商品版本，填写数量、码失效时间及备注。积分数与权益期限由版本决定，不能靠表单面值覆盖。
5. 一张追加体验码对应 5,000 积分，多份生成多个码。订阅积分包和并发包在用户兑换时检查有效套餐，发码本身不代表已获得资格。
6. 在“用户并发升级权益”查看逐码来源、期限及续期段；在积分批次中查看积分来源和到期时间，在商城查看连续续期后的最终到期时间。
7. 新积分包、体验包使用 `ADDON` 商品码；不要使用旧通用 `CREDIT` 码替代销售商品。旧码只保留兼容或人工发放用途。

### 6.3 运行时说明

- 初筛在批次结束后重新申请最新槽位；质量评价在篇/领域边界重新申请。已有请求不会因到期而中断。
- 并发请求重新申请前先释放该任务的旧租约，避免多个降档任务持有旧额度并互相等待。停止等待时清理队列/租约。
- 质量评价旧路径的模型线程数已受实际持有槽位限制；现有质量评价任务一次占用一个槽位，因此同一任务的旧路径多模型请求会串行执行，不再只占一个槽位却并行调用多个模型。升级包提高的是账户跨任务共享总上限，不把单个质量评价任务改成文献级并行。
- Redis 故障沿用现有槽位服务的降级策略，本次未重设计全平台故障策略。
